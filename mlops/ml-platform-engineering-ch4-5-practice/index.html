MLflow·Feast·Kubeflow를 잇기 - 소득 분류 배치 추론까지

October 31, 2026 · 37 min read
Jinwoong Kim
Technologist and Cloud Consultant

해당 포스팅은 현재 재직 중인 회사와 관련이 없고, 개인 역량 개발을 위한 스터디 자료로 활용할 예정입니다.

읽은 자료: Machine Learning Platform Engineering 4~5장(pp. 97–148). 스터디에서 참고한 내용과 실행 결과도 반영했다.
검증 환경: Ubuntu 기반 로컬 K3s 스터디 서버, MLflow 3.0.0, Feast 0.40.1, KFP 2.4.0, MinIO·Redis. 아래 결과는 스터디 실행 기록에서 확인한 값이며, 이 글을 쓰면서 새로 실행한 결과는 아니다.

4장의 실험은 MLflow에 남기고, 같은 모델이 쓸 피처는 Feast에 등록했다. 5장에서는 MinIO에서 대상자를 읽어 Feast로 피처를 가져오고, MLflow 모델로 추론한 뒤 결과를 다시 MinIO에 쓰는 네 단계 파이프라인을 실행했다. 스터디 기록에서는 네 작업이 모두 성공했고, 결과 파일은 30,162행 × 91열, 결측값은 0건이었다. 파이프라인의 예측값을 같은 등록 모델의 직접 추론과 비교했을 때 최대 차이는 0.0이었다.

막힌 지점도 남았다. 책의 MLflow 2.6.0 예제를 실습 환경의 3.0.0으로 실행하면서 모델 아티팩트 경로가 달라졌고, 실험에서 높은 AUC가 나온 XGBoost 모델은 5장 추론 코드의 predict_proba 인터페이스와 맞지 않았다. Feast에 저장한 localhost 주소는 Kubernetes Pod에서 통하지 않았으며, KFP 사용자 네임스페이스의 아티팩트 Secret이 없어 실행이 한동안 멈췄다. 이 글은 성공한 명령만 나열하는 대신 어느 연결이 왜 끊겼고 무엇을 확인해 해결했는지 따라간다.

1. 4~5장에서 연결하는 것​

1~2장에서는 모델의 정답·평가·리니지를, 3장에서는 컨테이너와 Kubernetes의 배포 경로를 봤다. 4장은 실험 결과와 피처를 다시 찾을 수 있게 만드는 장, 5장은 그 자산을 반복 가능한 배치 작업으로 묶는 장이다.

MLflow Tracking실행 ID, 파라미터, 지표, 입력 데이터의 메타데이터어느 실행에서 어떤 AUC가 나왔는가

MinIO데이터셋, 모델·플롯 아티팩트, 파이프라인 결과파일 자체가 저장되고 다시 읽히는가

Redis구체화한 온라인 피처 값현재 사용자 피처를 조회할 수 있는가

책의 그림 4.1은 플랫폼 전체에서 실험 추적·모델 등록·피처 스토어가 어디에 자리하는지 보여 주고, 그림 5.2는 배치 추론 때 이들이 어떻게 연결되는지 설명한다. 아래는 이번 소득 분류 사례에 맞춰 정보의 흐름을 새로 그린 것이다.

실험, 모델, 피처, 파이프라인은 서로 다른 자산이다. MLflow에서 실행이 끝났다고 Redis에 피처가 들어가지는 않는다. Feast에 피처 뷰를 등록했다고 배치 추론이 자동으로 시작되지도 않는다. 각 경계에서 무엇을 입력받고 무엇을 남기는지 확인해야 전체 흐름이 재현된다.

이번 실습에서는 MinIO의 버킷도 용도별로 나눴다. 이름을 알아두면 어느 단계에서 파일이 사라졌는지 좁혀 보기 쉽다.

이 글에는 책의 예제, 스터디에서 실제 확인한 결과, 아직 검증하지 않은 개선안을 구분해서 적었다. 예를 들어 KFP 파이프라인의 성공과 출력 파일은 실행 기록으로 확인할 수 있다. 뒤에서 제안하는 새 인코더 설계와 모델 별칭 전환은 다음 개선 작업이다.

2. 데이터부터 확인한다 - 4장 EDA​

import matplotlib.pyplot as plt

# 각 범주의 건수(stack)와 고소득 비율(fill)을 같은 데이터로 비교
plot_dir = Path("eda-plots")
plot_dir.mkdir(exist_ok=True)
for column in df.columns.drop("Target"):
    counts = pd.crosstab(df[column], df["Target"])
    ratios = counts.div(counts.sum(axis=1), axis=0)
    fig, axes = plt.subplots(1, 2, figsize=(14, max(4, len(counts) * 0.35)))
    counts.plot.barh(stacked=True, ax=axes[0], title=f"{column}: 건수")
    ratios.plot.barh(stacked=True, ax=axes[1], title=f"{column}: 비율")
    axes[1].set_xlim(0, 1)
    fig.tight_layout()
    fig.savefig(plot_dir / f"{column}.png", dpi=120)
    plt.close(fig)

Workclass에서 Private은 22,286건이다. 이처럼 범주의 크기가 크게 다를 때는 건수 그래프와 비율 그래프가 서로 다른 질문에 답한다.

  • position="fill"은 각 범주 안에서 <=50K와 >50K가 차지하는 비율을 보여 준다.

자영업 범주의 고소득 비율이 커 보이더라도 표본 수가 작으면 결과 해석은 달라질 수 있다. 그래프를 저장할 때도 제목에 변수 이름을 넣고, 사용한 데이터 버전과 생성 코드를 함께 남겨야 나중에 같은 그림을 다시 만들 수 있다.

분할과 인코딩도 실행 조건이다​

범주형 열은 더미 변수로 바꾸고 정답은 0/1로 인코딩한다. 스터디 코드에서는 여덟 범주형 열이 90개의 숫자 열이 됐다. column_list.pkl에는 그 열의 이름과 순서가 저장된다. 5장 추론 컴포넌트가 이 목록을 읽어 입력 열을 맞춘다.

import pickle
from sklearn.model_selection import train_test_split

features = df.drop(columns="Target")
encoded = pd.get_dummies(features, drop_first=True, dtype=float)
column_list = encoded.columns.tolist()
assert encoded.shape[1] == 90
with open("column_list.pkl", "wb") as file:
    pickle.dump(column_list, file)

target = df["Target"].astype(str).str.strip().eq(">50K").astype(int)
X_train, X_test, y_train, y_test = train_test_split(
    encoded, target, test_size=0.2, stratify=target, random_state=42
)
print(X_train.shape, X_test.shape)
print("고소득 비율:", y_train.mean(), y_test.mean())

원본 예제의 train_test_split에는 random_state가 없다. 실행할 때마다 학습·평가 행이 달라져 지표도 조금씩 바뀐다. 위 재현용 코드에는 random_state=42와 stratify=target을 넣어 세 모델을 같은 행과 클래스 비율에서 비교한다. 이 변경 때문에 아래 스터디 기록의 AUC 숫자와 새 실행의 숫자는 달라질 수 있다.

소득 데이터에는 성별·인종 같은 열도 포함돼 있다. 이 글은 책의 도구 간 연결을 공부하기 위한 예제다. 실제 의사결정에 쓰려면 예측 품질뿐 아니라 집단별 오류와 데이터 사용 기준을 별도로 검토해야 한다.

3. MLflow가 남기는 기록과 MinIO가 담는 파일​

책의 예제는 mlflow==2.6.0과 mlflow ui 명령을 쓴다. 스터디 실행 환경은 달랐다. MLflow 3.0.0 서버를 띄우고 SQLite를 백엔드 저장소로, MinIO를 아티팩트 저장소로 사용했다. 서버에 실험·실행·지표가 기록되고, 플롯·데이터셋·모델 파일은 객체 스토리지의 경로로 연결된다.

서버를 시작할 때는 메타데이터 저장 위치와 아티팩트 저장 위치를 따로 지정한다. 이번 재현 예제에서는 MinIO를 로컬 19000 포트로 연결한다. 첫 번째 터미널은 계속 열어 둔다.

kubectl -n kubeflow port-forward svc/minio-service 19000:9000

다른 터미널에서 MinIO 접속값을 Kubernetes Secret에서 읽는 스크립트를 만든다. 스크립트에는 값 대신 조회 명령만 들어간다. 이후 새 터미널을 열 때마다 이 파일을 source하면 Feast와 MLflow가 같은 MinIO에 접근한다. 필요한 버킷을 만든 다음 MLflow 서버를 실행한다. sqlite:///$PWD/mlflow.db는 현재 디렉터리가 ~/mlpe-study일 때 SQLite 파일을 그 안에 만든다.

4. 세 모델을 비교하니 모델 선택 기준이 달라졌다​

결정 트리, 랜덤 포레스트, XGBoost를 돌린 뒤 테스트 AUC를 비교했다. 스터디 화면에 남은 값은 다음과 같다. 실행마다 분할이 고정되지 않았으므로, 이 작은 점수 차이를 모델 간 우열의 확정 근거로 읽지는 않는다.

실행기록된 테스트 AUC읽을 때 확인할 것
결정 트리0.8200단일 트리의 확률로 계산
랜덤 포레스트0.85715장 배치 추론 코드와 인터페이스가 맞는 후보
원본 XGBoost 실행0.7248마지막 binary:hinge의 0/1 출력을 지표에 사용
분리한 XGBoost binary:logistic 실행0.8633확률을 사용했고, 별도 run에서 기록

ROC AUC는 양성과 음성을 점수 순서로 얼마나 잘 구별하는지 본다. binary:logistic은 확률을 반환하지만 binary:hinge는 0/1 클래스를 바로 반환한다. 후자의 AUC에 0/1 값을 넣으면 가능한 점수가 둘뿐이라 순위 정보가 크게 줄어든다. 원본 XGBoost 실행의 낮은 AUC만 보고 “XGBoost 모델이 약하다”고 결론 내리기 어려운 이유다.

더 큰 문제는 한 run 안에서 서로 다른 목적 함수로 xgb.train()을 두 번 호출한 것이었다. 첫 학습의 자동 기록과 둘째 학습의 수동 지표가 한 실행에 섞였고, 자동 로깅에서는 이미 기록한 파라미터를 다른 값으로 바꾸려 한다는 경고가 나왔다. 스터디에서는 binary:logistic과 binary:hinge를 별도 run으로 나눠 두 모델의 설정·지표를 각각 확인했다.

import xgboost as xgb

mlflow.xgboost.autolog()
dtrain = xgb.DMatrix(X_train, label=y_train)
dtest = xgb.DMatrix(X_test, label=y_test)
base_params = {
    "colsample_bytree": 1,
    "learning_rate": 1,
    "max_depth": 10,
    "subsample": 1,
}

for objective in ("binary:logistic", "binary:hinge"):
    with mlflow.start_run(run_name=f"xgboost-{objective.split(':')[1]}"):
        params = {**base_params, "objective": objective}
        model = xgb.train(params, dtrain, num_boost_round=30)
        scores = model.predict(dtest)
        labels = (scores >= 0.5).astype(int)
        auc = roc_auc_score(y_test, scores)
        accuracy = accuracy_score(y_test, labels)
        mlflow.log_metric("roc_auc_score_test", auc)
        mlflow.log_metric("test_accuracy", accuracy)
        print(objective, "AUC", auc, "accuracy", accuracy)

이 셀은 2절의 고정 분할을 이어받는다. binary:logistic에서는 확률을 임계값 0.5로 0/1로 바꿔 정확도를 구한다. binary:hinge의 점수는 이미 0/1이라 같은 식으로 계산해도 값이 바뀌지 않는다. 두 목적 함수의 AUC는 입력 점수가 확률인지 클래스인지 확인하며 읽어야 한다.

AUC 1등을 그대로 등록하지 않은 이유​

실행 목록에서 가장 높은 AUC는 분리한 XGBoost binary:logistic이었다. 하지만 책의 5장 추론 컴포넌트는 로드한 모델에 predict_proba()를 호출한다. xgb.train()으로 만든 XGBoost Booster는 그 메서드를 제공하지 않는다. 이 파이프라인을 고치지 않고 연결할 모델로는 사이킷런 랜덤 포레스트를 선택해야 했다.

여기서 구분할 기준이 두 개다.

  1. 평가 기준: 동일한 데이터와 지표로 어떤 모델이 업무 목표에 맞는가.
  2. 실행 계약: 등록 모델이 파이프라인의 입력 열과 predict_proba() 호출을 처리할 수 있는가.

스터디에서는 랜덤 포레스트 실행의 모델 종류를 확인한 뒤 random-forest-classifier 버전 1로 등록하고 Production 단계로 전환했다. 그 후 5장 코드는 models:/random-forest-classifier/Production을 사용했다. 이는 기존 예제와 맞추기 위한 선택이다. MLflow 공식 문서는 모델 단계(stage)를 더 이상 새 설계의 기본 경로로 권하지 않고 별칭(alias) 사용을 안내한다. 새 파이프라인에서 별칭을 쓰려면 모델 조회 코드도 함께 바꿔야 한다.

MLflow 3.0.0에서는 run의 고정 아티팩트 경로로만 모델을 찾으려 하면 등록 과정이 어긋날 수 있다. 스터디에서는 선택한 run에 연결된 logged model ID를 확인해 등록했다. 모델 이름을 random-forest-classifier라고 정하기 전에는 실제 저장된 모델이 랜덤 포레스트인지도 확인했다. 최고 점수 모델을 무조건 그 이름으로 등록하면 레지스트리의 이름과 내용물이 달라질 수 있기 때문이다.

아래는 위에서 실행한 random-forest run을 찾아 연결된 logged model을 등록하는 재현용 코드다. XGBoost run의 AUC가 더 높더라도 5장 컴포넌트가 요구하는 predict_proba()를 제공하는 후보를 명시적으로 선택한다. 같은 이름을 다시 등록하면 버전 번호가 1보다 커질 수 있으므로 출력된 버전을 확인한다.

from mlflow import MlflowClient

client = MlflowClient()
experiment = client.get_experiment_by_name("income-classifier")
runs = client.search_runs(
    experiment_ids=[experiment.experiment_id],
    order_by=["metrics.roc_auc_score_test DESC"],
)
rf_run = next(
    run for run in runs
    if run.data.tags.get("mlflow.runName") == "random-forest"
    and run.data.params.get("n_estimators") == "100"
)
logged_models = mlflow.search_logged_models(
    experiment_ids=[experiment.experiment_id],
    filter_string=f"source_run_id = '{rf_run.info.run_id}'",
    output_format="list",
)
if len(logged_models) != 1:
    raise RuntimeError(f"랜덤 포레스트 logged model 수: {len(logged_models)}")

registered = mlflow.register_model(
    f"models:/{logged_models[0].model_id}",
    "random-forest-classifier",
)
client.transition_model_version_stage(
    name=registered.name,
    version=registered.version,
    stage="Production",
    archive_existing_versions=True,
)
version = client.get_model_version(registered.name, registered.version)
assert version.run_id == rf_run.info.run_id
print(registered.name, registered.version, version.current_stage, version.run_id)

마지막 assert는 5장 추론 코드가 모델 버전의 run_id로 column_list.pkl을 찾아야 하기 때문에 넣었다. 실패하면 단계 승격만 확인하고 넘어가지 말고, 등록 모델과 실행 아티팩트의 연결부터 점검해야 한다.

Feast를 이해할 때 정의, 과거 값, 현재 값을 나눠 보면 덜 헷갈린다.

  • 오프라인 스토어: 과거 시점 조회에 쓸 Parquet 파일을 보관한다.

7. KFP 네 컴포넌트의 계약​

5장은 학습 파이프라인이 아니라 배치 추론 파이프라인을 만든다. 입력은 예측할 사용자 ID와 기준 시각의 목록이다. 출력은 각 사용자에 대해 모델이 계산한 고소득 확률을 담은 Parquet 파일이다. 네 작업은 하나의 DAG를 이룬다.

각 컴포넌트는 입력, 출력, 실행 이미지를 명세로 갖는다. 책의 예제는 Python 파일로 동작을 작성하고, Docker 이미지에 넣은 뒤, component.yaml에 파일 경로와 인수·아티팩트 타입을 연결한다. data_output을 Dataset으로 선언하면 다음 단계는 앞 단계의 outputs["data_output"]을 입력으로 받는다.

실습 저장소의 파이프라인은 KFP 2.9.0으로 컴파일돼 있었지만, 스터디 서버의 백엔드는 2.4.0이었다. 이번 실행에서는 백엔드 버전(2.4.0)의 SDK로 작업본을 다시 컴파일했다. 컴포넌트 이미지도 오래된 latest를 그대로 의존하지 않고, 실습에서 빌드한 고정 태그로 명세를 바꿨다. 원본 저장소 파일을 수정하지 않고 작업본을 둔 이유는 책의 예제와 환경별 변경을 비교하기 위해서다.

이제 소스 파일과 명세의 관계를 실제 경로로 확인할 수 있다. 2절에서 내려받은 chapter-5 저장소의 src/에는 네 작업의 Python 코드가, components/에는 각 코드의 입력·출력과 실행 명령을 적은 YAML이 있다.

# chapter-5-work/income_pipeline.py
from pathlib import Path
import kfp
from kfp import compiler, dsl

root = Path(__file__).parent
read_data = kfp.components.load_component_from_file(
    str(root / "components/read_data/component.yaml")
)
get_features = kfp.components.load_component_from_file(
    str(root / "components/retrieve_features/component.yaml")
)
infer = kfp.components.load_component_from_file(
    str(root / "components/run_inference/component.yaml")
)
write_data = kfp.components.load_component_from_file(
    str(root / "components/write_data/component.yaml")
)

@dsl.pipeline(name="income-classifier-pipeline")
def income_classifier_pipeline(
    minio_host: str,
    access_key: str,
    secret_key: str,
    entity_df_bucket: str,
    entity_df_filename: str,
    feature_store_bucket_name: str,
    feature_store_config_file_name: str,
    feature_list: str,
    model_name: str,
    model_type: str,
    model_stage: str,
    mlflow_host: str,
    output_bucket: str,
    output_file_name: str,
):
    ids = read_data(
        minio_host=minio_host, access_key=access_key,
        secret_key=secret_key, bucket_name=entity_df_bucket,
        file_name=entity_df_filename,
    )
    features = get_features(
        minio_host=minio_host, access_key=access_key,
        secret_key=secret_key, bucket_name=feature_store_bucket_name,
        file_name=feature_store_config_file_name,
        entity_df=ids.outputs["data_output"], feature_list=feature_list,
    )
    predictions = infer(
        minio_host=minio_host, access_key=access_key,
        secret_key=secret_key, model_name=model_name,
        model_type=model_type, model_stage=model_stage,
        mlflow_host=mlflow_host,
        input_data=features.outputs["data_output"],
    )
    write_data(
        minio_host=minio_host, access_key=access_key,
        secret_key=secret_key, bucket_name=output_bucket,
        file_name=output_file_name,
        input_data=predictions.outputs["data_output"],
    )

if __name__ == "__main__":
    compiler.Compiler().compile(
        pipeline_func=income_classifier_pipeline,
        package_path=str(root / "income_classifier_pipeline.yaml"),
    )

추론 입력 열은 목록만 맞춘다고 끝나지 않는다​

추론 컴포넌트는 Feast에서 얻은 범주형 값에 다시 pd.get_dummies(drop_first=True)를 적용하고, 학습 때 저장한 column_list.pkl의 열 순서로 맞춘다. 이 방식은 같은 범주가 모두 들어 있는 큰 배치에서는 작동할 수 있지만, 작은 배치에서는 조용히 잘못된 값을 만들 위험이 있다.

예를 들어 학습 전체에서 Occupation의 첫 범주가 A였고, 이번 배치에는 B와 C만 있다고 하자. drop_first=True가 이번 배치에서는 B를 기준 범주로 버릴 수 있다. 그 뒤 열 이름을 학습 목록에 맞춰 다시 정렬해도 버려진 B의 정보는 돌아오지 않는다. 결측 열을 0으로 채우는 작업은 인코더의 기준 범주를 고정하는 것과 다르다.

이번 실행은 전체 30,162행을 한 번에 넣어 직접 모델 추론과 같은 확률을 얻었다. 이는 그 배치에서 결과가 일치했다는 증거다. 새로운 한 명 또는 드문 범주만 들어온 배치에서도 맞는다는 보장은 아니다. 후속 개선에서는 학습 때 맞춘 인코더를 모델과 함께 저장하고, 추론에서도 같은 변환 객체를 사용해야 한다.

이 가정을 공개 데이터로 확인한 후속 실험에서는 같은 6,033명의 평가 데이터를 한 번에 추론할 때는 차이가 없었지만, 한 명씩 추론하자 1,229명의 0.5 기준 분류가 바뀌었다. 기존 KFP 실행과 별도로 모델을 새로 학습해, 배치 크기만 바꾸어 측정한 결과다. 이 배치 불변성 실험은 다음 글에서 따로 정리한다.

책의 소득 데이터에서 벗어나 수집부터 다시 해 보고 싶다면 한국어 뉴스 제목 분류 실험으로 이어진다. Hugging Face에서 KLUE YNAT을 내려받아 Rancher Desktop의 Kubernetes Job으로 학습·배치 추론하고, MLflow에서 모델을 등록했다. 이 실험도 별도 글로 다룰 예정이다.

8. 스터디 실행 결과와 막혔던 지점​

이전 정리에서는 KFP UI에 YAML을 업로드하고 화면에서 실행한 것처럼 읽혔지만, 제공된 실행 기록에는 REST API로 업로드·실행하고 결과를 확인했다고 적혀 있다. 당시 HTTP 요청을 담은 스크립트 원본은 확보하지 못했다. 아래에는 KFP 2.4.0의 공식 API 명세에 맞춰 새로 작성한 제출 명령과 결과 검증 코드 전체를 적었다. 이는 스터디에서 사용한 원본 호출을 그대로 복원한 것은 아니다. 스터디에서는 네 작업이 모두 Succeeded로 끝난 것과 MinIO 출력 파일을 확인했으며, Kubeflow 대시보드에서 동일 실행을 브라우저로 확인했다는 기록은 없다.

PIPELINE_ID="$(
  curl -fsS -X POST \
    "${API}/pipelines/upload?name=${NAME}&namespace=${KFP_NAMESPACE}" \
    -F "uploadfile=@income_classifier_pipeline.yaml" |
    jq -er '.pipeline_id'
)"
VERSION_ID="$(
  curl -fsS "${API}/pipelines/${PIPELINE_ID}/versions" |
    jq -er '.pipeline_versions[0].pipeline_version_id'
)"

# 2. 이 실행을 묶을 KFP 실험을 만든다.
EXPERIMENT_ID="$(
  jq -n --arg name "$NAME" --arg ns "$KFP_NAMESPACE" \
    '{display_name:$name, namespace:$ns}' |
    curl -fsS -X POST "${API}/experiments" \
      -H "Content-Type: application/json" --data-binary @- |
    jq -er '.experiment_id'
)"

# 3. 등록 모델과 피처 조회에 필요한 14개 런타임 파라미터를 보내 Run을 생성한다.
RUN_ID="$(
  jq -n \
    --arg name "$NAME" \
    --arg experiment "$EXPERIMENT_ID" \
    --arg pipeline "$PIPELINE_ID" \
    --arg version "$VERSION_ID" \
    --arg mlflow "$MLFLOW_HOST" \

      display_name: $name,
      experiment_id: $experiment,
      pipeline_version_reference: {
        pipeline_id: $pipeline,
        pipeline_version_id: $version
      },
      runtime_config: {parameters: {
        minio_host: "minio-service.kubeflow:9000",
        access_key: env.MINIO_ACCESS_KEY,
        secret_key: env.MINIO_SECRET_KEY,
        entity_df_bucket: "inference-datasets",
        entity_df_filename: "entity_df.parquet",

        model_type: "sklearn",

실행 파라미터에 비밀을 넣은 흔적​

책의 파이프라인 예제는 MinIO 액세스 키와 시크릿 키를 일반 문자열 파라미터로 받는다. 스터디 실행에서도 이 값이 KFP 실행 이력에 평문으로 남는 문제를 확인했다. 글에는 값이나 접속 가능한 주소를 옮기지 않았다. 공유 환경에서 재사용하려면 Kubernetes Secret 등 별도 경로로 주입하고, 파이프라인 파라미터에는 비밀 값을 넣지 않도록 컴포넌트 계약을 바꿔야 한다.

9. 두 장을 읽고 남은 운영 기준​

4장과 5장의 연결은 “도구를 모두 설치했다”보다 서로의 계약을 확인했다는 데 의미가 있다. MLflow run의 지표가 어느 데이터에서 나왔는지, 등록 모델이 추론 코드의 메서드를 제공하는지, Feast의 피처 주소가 실행 Pod에서 열리는지, 중간 Dataset이 다음 작업으로 전달되는지를 각각 확인했다. 결과 파일을 모델의 직접 추론과 대조한 것도 이 계약의 마지막 검사였다.

반면 이 파이프라인에는 재학습, 새 모델 승인, 실시간 서빙, 드리프트 감지가 아직 없다. 4장의 모델·피처 자산과 5장의 배치 추론은 MLOps 루프의 일부를 구현한다. 1~2장에서 정한 “운영에서 오류가 늘면 무엇을 고칠까?”라는 질문에 답하려면 예측 후 정답 수집과 모니터링, 새 후보 평가까지 이어야 한다.

다음에 같은 실습을 반복한다면 아래 네 가지부터 고치고 싶다.

  1. 평가 분할을 고정하고, 실행마다 데이터·변환·모델 버전을 함께 남긴다.
  2. 학습 시점에 맞춘 범주형 인코더를 추론 컴포넌트에서도 그대로 사용한다.
  3. 레지스트리의 stage 의존을 줄이려면 모델 별칭과 KFP 조회 코드를 함께 바꾼다.
  4. KFP 실행 이력에서 인증 값을 없애고, 네임스페이스 리소스 생성 문제를 수동 조치 없이 해결한다.
